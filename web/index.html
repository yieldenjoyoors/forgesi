A knot

A federated git host. Issues, pull requests, comments and labels are collaborative objects stored in the repository itself — plain git objects, public, portable. No VMs, no SSH daemons: Workers, D1, Artifacts.

A client

The console: the deck where humans see the fleet work, the todo board, proposals with machine verdicts. It consumes knot data like any Tangled client would.

An agent harness

The fleet: an orchestrator that assigns, sandboxed agents that implement, a machine reviewer that reacts first — so humans only look at the interesting parts.

How it works

  1. Write intent. A todo is a line in todo.md. One line, one task, versioned like everything else.
  2. The orchestrator assigns. Unassigned lines are its queue. It picks an agent and commits the @assignee.
  3. Agents work in proposals. An agent pushes a branch; a proposal is a ticket with a patch — the Tangled lexicons, end to end.
  4. Machine review first. An LLM reviewer reacts before a human ever looks. Everything is a plain text file and an ordinary commit.

Humans work on branches. Agents work in proposals.
Both land in git; only one needs your review.
